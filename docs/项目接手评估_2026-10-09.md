# 患者随访系统：项目接手与交付评估

评估日期：2026-10-09。基于当前工作区，包括尚未提交的本地改动。目的：判断项目实际完成度、交付障碍和后续开发顺序。

## 1. 结论

**当前项目是一个可运行的“患者建档、账号认领、资料上传与人工审核”试用原型，尚未成为能够开展长期随访和科研工作的完整系统。**

已经有价值的基础：后端权限范围检查、随机二维码令牌、核验码错误锁定、密码哈希、数据库迁移、须知版本及同意记录、带权限的原件读取、人工确认后的资料时间轴。这些可以继续使用，无须为追求技术形式推倒重写。

主要差距在业务层：没有疾病随访表、随访节点和任务，没有结构化诊断/用药/检验指标，没有科研队列、筛选和导出，没有真实 OCR，也没有知识库问答和诊后服务。现有基础流程自身还有明确断点和缺陷。

建议先把首期产品收敛成：**胃黏膜肠上皮化生患者资料管理与随访工作台**。这是医生设计构思已有的方向，不是另行替项目选择病种。先交付患者进得来、资料不丢、医生审得动、随访追得到、研究数据导得出的版本；AI 识别作为录入辅助接入。知识库问答等扩展应另设验收阶段。

这属于建议的范围调整。通用需求书仍将知识库问答列为 P0，若不正式调整，问答未完成就不能声称满足原定 MVP。

“阻断”表示扩大试用或接入真实数据前应解决；“高”表示直接影响日常工作；“中”表示应随相邻功能一起改善。它们是本报告的处理顺序，不与原需求书的版本优先级混用。

### 5.1 已复现的功能缺陷

| 编号/级别 | 触发方式与结果 | 业务影响 | 建议修复与验收 |

| B01 阻断：邀请并发认领 | 控制两个患者账号同时使用相同有效邀请及核验码；两次均返回 200、`bound=true`，但最终只有一个绑定，使用次数仍为 1 | 系统会向一个未保留绑定的账号错误报告成功，可能使已完成认领的归属被后写入覆盖。前提是双方持有相同邀请及核验材料，并非仅知道患者 ID 即可攻击 | 将可用状态判断、患者未绑定判断、扣减次数及绑定做成原子条件更新；并发请求仅一个成功，另一个明确冲突，绝不能换绑 |

| B04 高：失效会话使邀请页卡死 | 浏览器存在失效患者会话，认领接口返回 401；脚本操作不存在的 `accountFields` 元素，抛出 TypeError，提交按钮持续禁用 | 患者不能正常重新登录，页面没有可恢复提示；失效会话是常见场景 | 统一处理 401/403，恢复正确登录界面，在 finally 恢复按钮，保留必要填写内容；同时测试超时和停用两种情形 |

| 老年患者开户 | 设置两遍密码、输入核验码、记住随机 8 位账号；默认配置 30 分钟过期；没有找回入口 | 医护现场协助一次核验，之后通过明确的患者入口回访；设计可撤销的设备会话及可核验恢复方式，不靠患者记住随机编号 |
| 再次扫码 | 已用邀请显示失效/已使用，没有清楚的“去我的档案”路径 | 已认领本人可直接去患者中心；未登录先恢复身份；旧邀请不能重新绑定 |
| 提交材料 | 每份都先填日期、名称、说明，再选一个文件；多页报告要重复操作 | 主操作为“拍照/选资料”，允许连续多张、预览排序、旋转、删除重拍；尽可能从材料候选识别，患者只确认易懂信息 |
| 不知道报告日期 | 日期必填，默认今天；脚本用 UTC 取日期，中国时区凌晨还可能默认为前一天 | 允许“日期不清楚/仅年月”，保留日期精度，交给医务人员核对，不能默认把上传日当真实事件日 |
| 上传中断或离开页面 | 无进度、无草稿、无断点续传；错误时经常只显示通用或英文错误 | 保留未完成任务与文件状态，提供明确重试；登录恢复后回到当前任务，避免重新填写 |
| 医生审核报告 | 在患者长列表里逐人展开，再新开窗口看原件、返回填摘要 | 待审核队列直接进入“左侧原件、右侧字段和摘要”；支持下一份、草稿、明确驳回原因 |
| 查找患者 | 列表全量返回，没有搜索、筛选和分页 | 用必要的身份信息和院内/系统编号辅助定位；按待办、最近更新、病种筛选，服务端分页 |
| 拒绝建档申请 | 医生点击驳回，页面没有填写理由的流程 | 必须给患者一个可理解的理由与补交入口，不把驳回做成流程终点 |
| 确认内容有误 | 已审资料不能改，也不能记录为何撤销 | 更正保留旧版本，区分患者补充、医生确认与后续修改 |
| 二维码管理 | 只有当前生成的一个码可撤销；刷新就丢失当前管理状态 | 展示历史邀请及状态，能失效旧码、重新生成；不用重显已丢弃的明文令牌 |
| 家属代办 | 只有“家属协助”选项，账号却只能关联一名患者 | 正式设计被代理患者、代理人、授权范围和切换确认；没有设计完成前不要声称支持家庭多患者管理 |
| 理解页面 | 患者看到“OCR 未运行”、内部编号、模拟数据等实现说明，错误有时是英文或对象文本 | 试用说明集中展示；正常业务页只表达“已收到、医生待核对、需重拍、已确认”等状态；提供中文字段级错误 |

手机宽度下现有大按钮与单列布局基本可用，这部分可以保留。但大按钮不能弥补记账号、重复填表、审核入口深和失败无法恢复的问题。真实相机权限、HEIC 照片、微信浏览器和新窗口预览仍需真机验收。

## 9. 建议的交付顺序

### 第一批：修通基础流程

范围：B01—B08、B13—B16；同时设计身份和会话、统一资料模型。重点是认领、提交、审批、更正、失败恢复与可达测试环境。

验收：新患者提交后可查询状态；获批后首次原件和基本信息出现在同一患者档案；账号能受控认领；重复提交不会串人或重复入档；已审结果可追溯更正；两个账号并发认领不能覆盖；真实手机扫描试用地址能进入正确页面。

### 第二批：做出首个专病随访产品

范围：肠化患者基本信息、胃镜/病理、症状及分级、既往病史、幽门螺杆菌相关字段；人工结构化录入及审核；初诊/复诊记录；随访节点、缺失任务和医生集中工作台。

验收：一名虚构患者从初诊走到一次复诊，能看到前后记录和原件，知道哪些未填、谁负责补充、何时应随访。3/6/12 月节点来自医生构思，实际窗口、起算点和例外规则仍需医生确认后配置。

不要先造包罗所有病种的复杂表单平台。先把首个病种的版本化字段与流程做扎实，再抽象复用。

### 第三批：让科研数据可用，并完成受控运行底座

范围：患者检索、组合筛选、静态队列、字段完整性、Excel/CSV 与原件批量导出、团队授权；补齐加密、审计、会话安全、备份恢复和部署监控。安全与备份工程应从第一批并行推进，不能到最后才改数据模型。

验收：医生按已确认条件找出一批患者，预览并导出获授权字段；原始资料与导出记录能对应；另一名未获授权医生不能读取；从备份恢复后患者、资料、同意和审计保持一致。

### 第四批：接入经过验证的 AI 和诊后服务

优先接 OCR 候选字段提取，因为它直接减少第二、三批的人工录入量；它可以与前两批用去标识化样例同步开发，但正式入档仍须按规则确认。随后做普通咨询/加号工单、通知，再做知识库审核发布与带引用问答。加急咨询、录音、跨项目合并放在已有服务能稳定运行之后。

验收：用医生认可的样例集验证字段准确性和必须人工处理的场景；提取失败不伪造结果；问答无证据必须拒答且能转人工；通知失败能被发现、重试与处理。

不在尚未确定字段、验收标准、通知渠道和团队人力时承诺固定完工日期。第一批可以直接形成修复任务；其余批次在确认交付物后估算工作量，比按“功能名称个数”估工期可靠。

## 11. 技术上怎样继续最省返工

1. 保留 FastAPI、SQLAlchemy 和现有前后端接口式访问。当前不足不是因为没用某个前端框架；先修业务与状态管理，后续按页面复杂度决定是否重组前端工程。
2. 遵守项目现有 SQLite 边界，补受控写入、并发条件更新、一致备份与容量验证。现在没有证据要求立即换数据库，但也没有证据证明已满足目标负载。
3. 把建档附件与后续附件统一成“原件 + 归属/审核状态”模型，避免两条流程永久分叉。正式患者的基础资料需要自己的字段，不能长期寄存在待审核申请中。
4. 让疾病字段、随访记录、字段来源、审核版本及任务状态成为可查询数据。靠摘要文本无法可靠实现后续队列筛选、疗效分析和 Excel 导出。
5. 后端约 1400 行集中在 `main.py`。按身份/邀请、建档、文档、随访、队列等业务拆分，在修改相关模块时进行，不安排一轮与交付无关的大重构。
6. 上传目前用 JSON/Base64 整文件读入，约增加三分之一编码体积；多页报告场景应改为适合文件传输的接口与明确任务状态，评估实际内存、并发和超时。
7. 列表目前多处 `.all()` 全量读取；新增分页和过滤。健康检查目前只返回固定 `ok`，应补数据库、存储和作业就绪状态以及业务失败告警。
8. 现有 13 项测试主要覆盖邀请、权限范围、同意版本、单资料审核；测试身份还绕过了真实登录依赖。补关键端到端、并发、错误恢复、迁移、文件与恢复测试，而不是只增加“接口返回 200”的数量。
9. 增补 README、环境初始化、配置说明、测试方法、部署/回滚、备份恢复、当前版本功能及未完成清单。学习调研文档和模型示例脚本不应继续充当项目交付计划。

## 12. 可以直接作为验收清单的场景

- 同一设备先后帮助两名患者申请，两人的内容、材料和回执各自独立。
- 同一申请因弱网重试只产生一条记录；内容改变不被静默当成旧申请。
- 两账号同时认领一个邀请，只有一个成功，原绑定不被覆盖。
- 邀请过期、会话失效、权限撤销后，页面给出明确恢复路径。
- 建档获批后，原始材料、基本资料、同意记录和患者归属可从档案追溯。
- 上传多页报告或中断重试，不丢页、不乱序、不重复入档。
- 医生集中看到待办，逐字段确认，修改有历史，驳回有原因。
- 随访日期与窗口正确计算，缺项、未知和未检查分开记录。
- 研究筛选和导出只包含获授权范围及允许字段，操作可追溯。
- 隔离恢复数据库和原件后，抽样校验档案、时间轴、原件与审计一致。
- AI 失败、无证据、过期知识等情形不会生成冒充已确认的数据或答案。

项目的完成标准应当是这些流程可验收，而不是页面数量、模型能回复，或现有单元测试全部变绿。
