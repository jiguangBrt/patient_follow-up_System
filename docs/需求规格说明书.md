## 1. 文档目的

本文档将医生提出的随访、病历管理、科研队列和诊后咨询需求整理为可讨论、可拆分、可验收的产品需求。它用于统一医生、科研团队和开发团队对系统范围的理解，不替代临床规范、伦理审查、知情同意文本或正式的数据合规评估。

本文档中的“必须”表示首期上线前不可缺少的安全或业务能力；“应”表示计划能力；“可”表示后续增强能力。

## 2. 项目背景与产品目标

患者门诊结束后获得一个专属二维码。患者扫码进入移动端网站，完成身份核验和知情同意后，上传本次及后续检查、化验和病历材料。系统把材料持续归入正确患者的时间轴，并按疾病随访模板提取关键指标。

医生端围绕患者、疾病和治疗方案建立长期科研队列，查看个体疾病演变、疗效指标和队列统计。患者可使用基于医生审核知识库的在线问答；系统只有在检索到可靠依据时才能回答，否则明确拒答并给出合适的人工咨询路径。

主要目标：

1. 建立患者从门诊结束到长期随访的连续数据链路。
2. 以病历原件为依据，形成按时间排序、可追溯的个人病历包。
3. 通过疾病模板保证疗效评价所需关键字段尽量完整。
4. 支持个体病案生成、同类患者队列筛选和科研数据提取。
5. 提供有来源、可追溯、能拒答的诊后知识问答。
6. 在严格授权、审计和去标识化的前提下支持团队协作及未来的跨医师研究。

## 3. 产品原则

1. **原始材料优先**：AI 提取结果不能替代患者上传的病历、影像报告或化验单原件。
2. **人机协同**：低置信度、相互冲突或影响疗效评价的字段必须由患者或医务人员确认。
3. **最小权限**：任何用户只能访问完成当前任务所必需的数据。
4. **全程可追溯**：关键数据的来源、修改、审核、导出和访问均应留痕。
5. **无依据不回答**：虚拟医师不得凭模型常识补全答案；可靠依据不足时必须拒答。
6. **紧急情况优先分流**：机器人不得承担急救判断或延误线下就医。
7. **科研与诊疗分离**：科研数据使用、共享和导出必须有独立权限、审批依据及去标识化策略。
8. **移动端优先**：患者核心流程应适合扫码后在手机浏览器中完成。

## 4. 用户角色与权限边界

### 4.1 角色定义

| 角色 | 主要职责 | 权限边界 |
| --- | --- | --- |
| 核心医师 | 系统业务负责人；管理患者、队列、模板、团队和知识库 | 可访问授权范围内的完整临床数据；授权或撤销团队成员；审批知识和科研导出 |
| 授权医师/科研团队医师 | 协助录入、审核、疑难问题处理及特定研究 | 仅访问被分配的患者、队列或字段；不可自行扩大权限 |
| 患者 | 上传、查看和补充本人材料；发起咨询和服务申请 | 仅访问本人数据和允许患者编辑的内容；不可查看内部科研标签和他人数据 |
| 运维管理员 | 账号、部署、备份和故障处理 | 默认无权读取病历正文和咨询内容；临时排障访问须审批并审计 |

### 4.2 权限模型

系统采用“角色权限 + 数据范围”双层授权，不能只根据页面入口判断权限。

数据范围至少包括：本人、指定患者、指定队列、指定研究项目、核心医师全部患者。对查看原件、编辑结构化字段、审核 AI 结果、回答咨询、管理知识库、导出数据、管理成员分别授权。

授权必须有授权人、被授权人、范围、用途、开始时间、失效时间和撤销记录。患者转组、成员离组或研究结束后，应能立即撤销访问。

## 5. 业务范围与版本划分

### 5.1 首期 MVP：形成最小闭环

首期必须完成以下业务闭环：

1. 医生或工作人员创建患者、一次就诊及专属二维码。
2. 患者扫码、核验身份、签署当前版本知情同意书。
3. 患者拍照或选择文件上传病历、检查及化验材料。
4. AI 识别材料类型、日期和关键字段；患者或医务人员核对后入档。
5. 系统按时间轴展示患者病历，并按疾病模板收集必填随访字段。
6. 缺失或异常待核实字段形成任务并通知对应医务人员。
7. 医生按诊断、治疗药物、时间及关键指标建立和筛选队列。
8. 患者发起诊后问答；系统基于已审核知识库回答或拒答。
9. 医生处理机器人无法回答的问题，并将合适内容沉淀为待审核知识。
10. 系统提供访问审计、加密备份和恢复验证。

### 5.2 第二阶段

1. 疗效标准配置、个体趋势图、队列聚合统计和标准化科研导出。
2. 检查节点、复诊节点和自定义事件提醒。
3. 一般应急联络、一次紧急联络服务及处理工单。
4. 预约、取消预约、限量加号及停诊定向通知。
5. 录音转文字、事件提取和提醒建议，须经患者确认后创建。
6. 疑难问题协作和授权医师工作台。

### 5.3 后续阶段

1. 在协议和审批机制完备后进行跨医师、跨研究项目的数据合并。
2. 中药处方的药名、剂量、炮制、用法和方剂变化结构化提取。
3. 科普知识模块。
4. 与院内电子病历、检验、预约或消息平台集成。
5. 更复杂的统计分析或经验证的研究模型。

### 5.4 当前不在范围内

1. 由系统自动诊断、开具处方或调整治疗方案。
2. 由机器人提供急救处置或保证医生实时响应。
3. 将 AI 提取内容未经确认直接写成正式临床结论。
4. 直接控制医院号源、支付、医保或处方流转，除非后续获得正式接口。
5. 本阶段生产部署、真实患者数据迁移和院内系统对接。

## 6. 核心业务流程

### 6.1 门诊后建档与二维码

系统支持两种受控入口：

1. 已有患者：医务人员创建或选择患者及就诊，系统生成随机、不可猜测、可失效的患者专属二维码邀请。
2. 新患者：医务人员生成可轮换、可撤销的通用建档二维码；患者扫码后只能提交待审核建档申请，不能读取患者库或自动创建正式档案。
3. 通用建档申请只收集最少基本信息；纸质病历信息优先通过后续拍照和人工/OCR审核处理，不要求患者一次性手工抄录。
4. 医生审核申请并检查潜在重复档案后，才能批准创建正式患者档案、指定负责医生并绑定提交账号；不得自动合并或静默覆盖。
5. 系统为已有患者创建本次就诊记录，并生成患者专属邀请。
6. 两类二维码中均不得直接包含姓名、证件号、手机号、病案号或连续患者 ID。
7. 患者专属邀请扫码后进行二次身份核验，核验通过后才可绑定账号或当前设备会话。
8. 首次进入必须阅读并签署当前版本知情同意书；未同意时不得上传或进入后续服务。
9. 邀请或通用建档链接使用、过期、撤销或达到次数限制后，服务端必须按规则使其失效。

### 6.2 病历上传与归档

1. 患者选择材料类型或直接上传照片/PDF。
2. 系统完成病毒/恶意文件检查、格式校验、清晰度检查和文件加密存储。
3. AI 识别材料类型、医疗机构、报告日期、检查项目、结果、单位、参考区间、诊断和用药等候选字段。
4. 每个字段保留原文、来源页码或图片区域、提取值、置信度及模型版本。
5. 患者可确认明显信息；临床关键字段和低置信度字段进入医务人员审核队列。
6. 确认后的材料进入按“事件发生日期”排序的病历时间轴；上传时间同时保留。
7. 原始文件永不被结构化结果覆盖，重复上传、修订和作废均保留版本记录。

### 6.3 疾病随访与关键字段补全

1. 医生为患者选择一个或多个疾病随访模板。
2. 模板定义一般信息、既往史、临床症状、四诊信息、疾病特异指标、疗效评价时间点和必填规则。
3. 系统尝试从已确认资料中匹配字段，并显示来源和时间。
4. 某时间点字段缺失、超期或存在冲突时，生成补录任务并指派给当时负责的授权医师。
5. 医务人员补录必须标明数据来源；无法获得时使用“未知/未检查/患者未提供”等明确状态，不得用空值代替。
6. 模板变更必须版本化，历史记录继续使用当时的模板与评价规则。

### 6.4 在线问诊与知识库问答

1. 患者选择诊后问题类型并输入问题，界面明确该功能的服务边界。
2. 系统先执行紧急风险词和场景分流，再进行知识检索。
3. 问答只能检索处于“已审核、已发布、未过期”状态且适用于当前患者范围的知识。
4. 回答必须附内部可追溯的知识条目、版本和引用片段；患者端至少显示易理解的来源名称和更新时间。
5. 检索相关性、证据覆盖度或知识状态不满足阈值时，系统返回统一的“不具备可靠依据，暂不回答”，不得让通用模型自由补答。
6. 涉及个体化诊断、药物增减停用、严重不良反应、急症判断等问题，默认转人工或提示线下就医。
7. 拒答或患者申请人工服务时形成工单，由有权限的医师处理。
8. 医师答复可被整理为候选知识，但必须经过独立审核和发布流程后才能被机器人复用。

### 6.5 紧急联络

1. 患者主动选择“紧急联络”或系统识别到高风险表述时，立即显示预先审核的紧急提示和线下求助方式。
2. 页面必须说明平台不是急救通道、医师不保证实时在线；可能危及生命时应优先联系当地急救服务或就近就医。
3. 系统记录患者发起时间、风险分类、联系方式、通知对象、接单时间、处理结果和关闭人。
4. “一次紧急联络医师”的次数、有效期、服务时间和用尽后的路径由业务方确认后配置，不能写死在前端。
5. 紧急工单的通知失败、超时和升级规则必须可监测，不能只依赖站内消息。

### 6.6 科研队列与数据提取

1. 核心医师可按诊断、治疗药物、随访时间、疗效字段和其他获批标签创建动态或静态队列。
2. 每个队列记录研究目的、纳入标准、排除标准、负责人、成员、数据范围和有效期。
3. 患者纳入或移出队列应有原因及操作记录；动态队列应保留每次分析时的规则版本和数据快照标识。
4. 系统支持查看队列规模、完整性、随访完成率及关键指标分布。
5. 导出前执行权限校验、字段最小化和去标识化；导出任务、文件下载及过期删除均被审计。
6. 不同医师数据合并必须依附具体研究项目、共享协议和患者授权/伦理依据，不能因账号属于同一机构而自动合并。

## 8. 信息架构与页面需求

### 8.1 患者端

患者端采用移动端优先的网页。考虑到主要使用人群可能包括不熟悉复杂手机操作的老年患者，首期采用“一次只完成一个任务”的单列流程；疾病队列选择、临床字段确认和其他专业判断由医务人员在医生端完成，不要求患者自行分类。

首期核心页面压缩为：

1. 扫码落地页及身份核验。
2. 知情同意书阅读与签署页。
3. 当前任务页：首次默认只提示拍摄或选择一份资料。
4. 拍照预览、重拍、提交及完成状态。
5. 简化的病历时间轴和资料状态。

首次绑定应支持医务人员在门诊现场协助完成。患者已经具有有效设备会话时，不应重复要求输入账号、密码和邀请核验信息。长表单按任务拆分、自动保存，并尽可能使用大按钮、明确文字和手机数字键盘。

第二阶段再增加随访表单、个人设置、授权记录、同意撤回和账号安全；知识问答、紧急联络、预约/取消、加号、录音事件和通知中心按确认后的优先级后移。

### 8.2 医生端

医生端以高信息密度的工作台为主：

1. 今日待办：待审核材料、缺失字段、人工咨询、紧急工单和逾期任务。
2. 患者列表及患者详情：概览、时间轴、随访、指标趋势、咨询、权限和审计。
3. 队列管理：筛选器、成员、数据完整性、分析、导出。
4. 随访模板及疗效标准管理。
5. 知识库：导入、编辑、审核、发布、复审、停用和问答命中分析。
6. 团队与权限管理。
7. 系统备份状态和恢复演练记录（仅相应管理权限可见）。

### 8.3 授权医师端

授权医师登录后只显示其被分配的工作：

1. 疑难问题处理。
2. 指定患者数据录入和 AI 结果审核。
3. 缺失字段补录任务。
4. 获批队列的查看、筛选及有限导出。

| AI 处理 | 处理任务、模型版本、提取字段、字段证据、置信度、审核记录 |

### 9.2 数据质量规则

1. 临床字段区分“未填写、未知、未检查、不适用、等待审核”，不能全部存为空值。
2. 检验值同时保存原始文本、结构化数值、单位和参考区间；单位换算不得破坏原始值。
3. 所有临床事件至少记录事件日期精度；只知道月份时不得伪造具体日期。
4. 诊断和药物保留原文，同时可映射标准术语；映射结果注明人工或自动及版本。
5. 每个派生指标保存算法/标准版本、输入项、计算时间和结果。
6. 删除原则上采用业务作废或受控删除，关键临床和审计数据不得静默覆盖。

### 9.3 SQLite 使用约束

1. SQLite 是首期唯一业务关系数据库，不引入独立数据库服务器。
2. 后端统一访问 SQLite，浏览器和前端不得直接读取数据库文件。
3. 必须启用外键约束，使用事务保证患者、文档、字段和审计记录的一致性。
4. 根据验证结果启用 WAL 模式和受控连接，避免多个服务实例无协调地同时写同一数据库文件。
5. 数据库文件不得放在不支持可靠文件锁的共享网络目录中。
6. 病历图片、PDF 和录音不建议作为大 BLOB 直接写入 SQLite；首期存放在受控加密文件目录，SQLite 保存不可猜测标识、路径引用、哈希、密钥引用和元数据。备份时二者必须作为一致备份集。
7. 数据库结构变更必须通过版本化迁移执行，并在迁移前创建可恢复备份。
8. 在确认预计患者数、日上传量、并发写入和保留周期后进行容量及压力测试；超出验证边界时重新评估架构。

## 10. 前后端分离与接口边界

### 10.1 总体约束

1. 患者端和医生端为独立前端应用或同一前端工程中的独立入口，通过 HTTPS API 访问后端。
2. 后端负责身份认证、权限判定、业务规则、文件授权、AI 任务编排、审计和 SQLite 访问。
3. 所有安全判断均在后端执行，前端隐藏按钮不等于权限控制。
4. API 使用明确版本，例如 `/api/v1`；请求、响应和错误格式保持一致。
5. AI/OCR、通知和文件存储通过后端适配接口接入，避免供应商逻辑散落在前端。

### 10.2 首期接口域

| 接口域 | 示例能力 |
| --- | --- |
| 认证与邀请 | 登录、刷新/撤销会话、解析二维码、身份核验、绑定 |
| 同意管理 | 获取当前文本、签署、查询记录、申请撤回 |
| 患者与就诊 | 患者建档、详情、就诊创建、负责医师 |
| 文档 | 发起上传、完成上传、处理状态、时间轴、授权下载 |
| AI 审核 | 查看候选字段、确认、修正、驳回、重新处理 |
| 随访 | 模板、患者表单、字段来源、缺失任务、指标趋势 |
| 队列研究 | 条件筛选、保存队列、成员、汇总、导出任务 |
| 知识问答 | 知识管理、审核发布、发起会话、回答、转人工 |
| 服务 | 工单、紧急联络、提醒、预约、通知 |
| 管理审计 | 成员授权、审计查询、备份与恢复状态 |

接口详细字段、状态码和 OpenAPI 契约在技术设计阶段另行编制。

## 11. AI 能力与安全护栏

### 11.1 文档识别

1. AI 输入必须来自已授权患者材料，任务完成后按约定处理第三方缓存。
2. 对任何外部 AI 服务发送患者信息前，必须完成供应商、数据位置、留存和二次使用评估；未批准前使用脱敏样例或本地方案开发。
3. 文档类型识别与字段提取应分别评测，按材料类型统计准确率、漏检率和人工修正率。
4. 置信度只用于分流，不能被描述成临床正确概率。
5. 模型或提示词升级后保留版本，并用固定测试集回归验证。

### 11.2 知识问答

回答生成需经过以下控制链：

1. 问题风险分类。
2. 患者数据访问范围校验。
3. 从已发布知识中检索候选证据。
4. 校验证据相关性、时效、适用人群和冲突。
5. 在证据范围内组织回答并绑定引用。
6. 输出前检查越界内容、个体化治疗建议和紧急风险。
7. 不满足任一关键条件时拒答或转人工。

知识库最小管理字段包括：标题、正文、来源、适用疾病/人群、禁忌或排除条件、作者、审核人、发布日期、复审日期、版本、状态。

### 11.3 AI 验收基线

在选定首批病种和材料后建立去标识化测试集，并由临床人员定义：

1. 每类文档的分类准确率目标。
2. 每个关键字段的准确率、召回率及允许误差。
3. 必须转人工的风险问题集合。
4. 必须拒答的无知识、冲突知识和过期知识集合。
5. 回答引用正确率和无依据陈述率目标。

具体数值不能由开发团队单方面设定，应在临床风险分级后补入验收方案。

## 12. 安全、隐私与合规需求

1. 生产环境全程使用传输加密；敏感字段和上传文件静态加密。
2. 姓名、证件信息、手机号、详细地址等直接身份信息采用应用层字段加密；密钥与 SQLite 数据库和备份分离保管。
3. 密码只保存强哈希；二维码令牌、重置令牌等敏感令牌只保存不可逆摘要或等效安全表示。
4. 文件下载使用短期授权，不暴露真实服务器路径。
5. 防止越权访问、批量枚举、恶意上传、注入、跨站请求、跨站脚本和暴力登录。
6. 日志不得记录完整证件号、密码、二维码令牌、会话令牌和病历正文。
7. 高风险操作包括授权、导出、删除、知识发布和恢复，应要求再次确认或二次认证。
8. 定义数据保留、患者撤回、账号注销、数据更正、研究冻结和删除例外的正式规则。
9. 上线前由医疗机构确认适用的伦理、隐私、网络安全、数据跨境及医疗服务规定，并完成所需评审。
10. 开发、测试和演示环境不得使用未经处理的真实患者数据。

## 13. 非功能需求

### 13.1 性能与容量

1. 除文件上传和 AI 任务外，常规页面/API 在目标负载下应提供可接受的交互响应；具体百分位指标待容量估算后确定。
2. 上传和 AI 处理采用异步状态，不阻塞患者继续浏览。
3. 列表、时间轴、审计和队列查询支持分页，禁止无上限拉取。
4. 首期上线前以预计峰值并发、每日上传量、单文件上限和五年数据量进行压力与容量测试。

### 13.2 可用性与兼容性

1. 患者流程兼容主流手机浏览器，关键操作不依赖悬停或桌面端布局。
2. 上传中断、AI 失败、通知失败和会话过期均给出可恢复状态。
3. 表单自动保存草稿；重复提交不得产生重复就诊、工单或预约。
4. 重要状态不只依靠颜色表达，表单错误能定位到具体字段。
5. 患者端每屏只设置一个主要操作，不要求患者理解疾病队列、科研字段或 OCR 置信度等专业概念。
6. OCR 未识别到内容时只能标记为“未识别/待确认”，不得自动推断为患者不存在该症状或临床情况。

### 13.3 可维护性与可观测性

1. 前端、后端、AI 适配、数据迁移和备份脚本职责清晰。
2. 业务日志使用请求/任务关联标识，能串联上传、AI、审核和入档过程。
3. 监测登录异常、任务积压、AI 失败、磁盘容量、备份失败、通知失败和紧急工单超时。
4. 配置和密钥不得写入源码仓库；不同环境独立配置。

### 13.4 备份目标

恢复点目标（RPO）、恢复时间目标（RTO）、备份频率、异地副本、保留周期和演练频率由业务方根据可接受的数据损失确认。未确认前，不以“已生成备份文件”视为备份能力验收通过，必须实际完成恢复演练。

## 14. MVP 端到端验收场景

1. **正确建档**：工作人员创建患者和就诊，患者扫码并二次核验后只能看到自己的同意书和资料。
2. **失效二维码**：已撤销、过期或超次数的二维码无法绑定，也不泄露患者是否存在。
3. **资料入档**：患者上传一份多页报告，系统保留原件，提取日期和关键指标，经确认后正确进入时间轴。
4. **低置信度处理**：模糊报告不会自动生成已确认临床值，而是提示重传或进入人工审核。
5. **关键字段补录**：随访模板要求的字段缺失时，系统给对应授权医师生成任务并在完成后关联来源。
6. **可靠回答**：知识库存在已发布且适用的条目时，患者获得带来源的边界内回答。
7. **安全拒答**：知识缺失、过期、冲突或问题要求个体化用药决策时，系统不生成推测答案并提供人工路径。
8. **权限隔离**：授权医师无法通过修改 URL/API 参数访问未分配的患者、队列、原件或导出文件。
9. **队列提取**：核心医师保存组合筛选条件、创建队列并导出去标识化字段，操作全程可审计。
10. **备份恢复**：从一个加密备份集恢复 SQLite 和文件，抽样患者的时间轴、原件及审计记录一致。

## 16. 待确认问题

以下问题会直接影响产品边界、数据结构或安全方案，应在开发相应模块前由指定负责人确认。

### 16.1 临床与科研

1. 首期选择哪一个或哪几个病种？每个病种采用哪套疗效评价标准及版本？
2. 一般信息、既往史、症状、四诊和疾病特异字段的完整数据字典是什么？
3. 哪些字段由门诊医生当场填写，哪些允许患者补充，哪些只能由医务人员确认？
4. “及时反馈”的目标时限是多少，任务应指派给首诊医师、当前负责医师还是队列负责人？
5. 首期需要哪些统计图、分析口径和导出格式？是否只做描述性统计？
6. 中药信息首期只保留处方原文，还是必须结构化到药物、剂量、炮制和用法？
7. 跨医师数据合并由什么研究项目、审批和患者授权机制支撑？

### 16.2 患者身份与服务

1. 患者主索引使用院内病案号、证件信息、手机号还是系统内部编号？如何处理重复患者？
2. 二维码由谁、在何处创建和打印/展示？有效期和可使用次数是多少？
3. 扫码后的二次核验采用短信验证码、预留信息、人工核验还是其他方式？
4. 患者能否代家属操作？未成年人或无行为能力患者如何记录监护/代理关系？
5. 知情同意书由谁提供和审核？诊疗服务、科研使用和 AI 处理是否分别同意？
6. “一次紧急联络”按患者终身、单次就诊、年度还是服务包计算？服务时间和升级渠道是什么？
7. 预约、加号、停诊通知使用哪些真实渠道，是否已有可对接的平台？
8. 提醒通过短信、微信、电话还是站内通知发送？谁承担消息费用和失败处理？

### 16.3 AI 与知识库

1. AI 是否允许调用外部服务？若允许，可发送哪些数据，数据能否离开指定环境？
2. 首期要识别的文档样式、语言、图片/PDF 上限和目标准确率是什么？
3. 知识来源包括指南、论文、医生原创内容还是内部答复？各类来源的审核与复审周期是多少？
4. 谁是知识发布审核人？发布是否要求双人审核？
5. 机器人可以使用患者个体数据到什么程度：仅做知识范围筛选，还是允许在规则下复述已确认指标？
6. 哪些问题必须拒答，哪些可以转授权医师，人工答复时限是多少？

### 16.4 数据、安全与运行

1. 预计首年患者数、五年患者数、日上传量、峰值并发和单患者平均文件量是多少？
2. 数据保留多久？患者撤回、死亡、研究结束或账号注销时分别如何处理？
3. 线下服务器的操作系统、磁盘容量、磁盘加密、机房访问和异地备份条件是什么？
4. 可接受的 RPO、RTO、备份频率和恢复演练频率是多少？
5. 是否需要与医院统一身份、病历、检验、预约或科研平台对接？接口是否可用？
6. 开发、测试和临床验收分别由谁负责，是否能提供去标识化测试数据？

## 17. 首轮评审建议

建议第一次需求评审只做三项决策：

1. 确定首期病种、随访节点和一套疗效评价标准。
2. 走通“建档发码—患者核验—同意—上传—审核—入时间轴—缺失补录”的真实线下流程。
3. 明确知识库第一批内容、允许回答范围、必须拒答范围及人工承接人。

上述三项确定后，再输出首期数据字典、页面流程图、权限矩阵、接口契约和迭代任务清单。
