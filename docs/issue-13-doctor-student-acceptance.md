# 医生与学生账号、患者授权验收

本轮对应 #13 的医生团队账号与患者权限部分（#35 的患者范围能力）。业务角色称为“医生”和“学生”；原医生账号不改名、不迁移患者。学生归属一位医生。医生和学生共用 `/doctor`、`/clinical` 工作台，后端逐次检查权限。

登录页仅有“患者 / 医生团队 / 管理员”三个入口。医生团队登录由后端查询账号真实身份，医生和学生仍共用工作台，按真实角色显示操作。旧 `?role=doctor` / `?role=student` 登录链接自动选中医生团队。

## 已实现的范围

- 管理员侧栏区分“全部账号”“医生账号”“学生账号”，列表支持类型/状态筛选，显示学生所属医生、上次登录；开通学生必须选择启用的医生。
- 医生在“设置 → 学生与权限”查看学生列表，通过右上角“新增学生”弹窗开通账号，通过学生行的“分配权限”与“授权记录”弹窗分配患者、撤销授权；可启停自己的学生。学生不能再开账号、授权、新建患者或管理患者二维码。
- 授权记录保留授权人、学生、患者、用途、开始/结束时间、撤销人和撤销时间。权限变更采用撤销旧记录、再新增记录，保留历史。多条有效授权的权限取并集。
- 新学生默认无患者权限。授权未开始、已到期或撤销时，下次请求立即拒绝；学生或所属医生停用后，已有登录也不能再请求业务接口。已在浏览器显示或已下载的内容无法追溯收回。
- 查看、录入、审核分别控制：录入支持患者范围内上传、OCR 和待确认草稿；审核允许确认入档、批准/驳回和补充已归档资料的待确认字段。没有审核授权不能通过改请求确认字段。
- 学生上传必须先选有录入授权的患者；原件归属医生，在同一工作区对医生可见。学生不能查看医生的未分配缓冲区资料，也不能将患者原件归到其他患者。
- 原件、预览、资料列表、建档申请、患者档案、OCR、暂存、确认和审核历史均检查患者授权；OCR 返回前再次检查，运行中撤权时不保存识别结果。
- 新增迁移 `c83e2a17d604`。旧账号保持原角色。存在学生账号或授权历史时拒绝自动数据库降级，避免丢失记录。

## 真人验收（公网或本机均可）

仅用虚构资料。在两个独立浏览器窗口登录医生和学生，避免反复切换身份。可以使用现有医生账号；学生账号在测试中自行创建、密码自行设置。

1. 管理员登录：分别点击侧栏“医生账号”“学生账号”，确认过滤正确；在“开通账号”选学生，不选所属医生应无法提交。选一位启用的医生后开通，列表中应显示学生与所属医生。运维管理员不能直接访问病历接口。
2. 医生登录：从“医生团队”入口登录，进入“设置 → 学生与权限”，点击右上角“新增学生”弹窗开通另一名学生。两次初始密码不一致应阻止提交；成功后密码清空、隐藏。只能看见本医生的学生。
3. 医生在患者管理新增“测试甲”和“测试乙”。暂不分配权限，学生也从登录页选择“医生团队”登录，后端根据账号自动识别为学生，应进入同一工作台，但患者列表为空。
4. 医生点击该学生行的“分配权限”，在弹窗中给学生分配“测试甲”，填写用途和有效期，先只授予查看。学生刷新后能看甲，看不到乙；无新建患者、二维码或团队管理入口。持有乙的患者 ID 或原件链接也不能访问。
5. 撤销旧授权，再给甲授予“查看 + 录入”，不授予审核。学生到“病例识别与审核”选甲后上传虚构 PNG/PDF，运行 OCR，核对后点击“暂存”。重新打开应保留草稿；“确认并入档”“驳回”应不可用。医生能看见学生上传的原件和草稿，并完成确认归档。
6. 如需要学生协助审核：撤销旧授权，新增包含“审核”的授权。学生可在甲的原件上确认入档；仍不能新建患者或分配给乙。测试前核对姓名和就诊日期。
7. 学生保持已登录，医生打开该学生行的“授权记录”弹窗，撤销甲的全部有效授权。学生刷新患者列表后甲应消失；再次打开先前资料、预览或原件链接应被拒绝。已有多条授权时，只撤销一条不会取消其他有效授权。
8. 新增一条未来开始的授权：生效前学生看不到；再测试一个短有效期授权，到期后再次请求被拒绝。时间输入按本机时区转换，记录表按北京时间显示。
9. 医生停用学生：学生现有页面再次请求应失去登录访问，重新登录也应失败。管理员停用所属医生时，该医生的学生也应无法继续访问。

本机隔离环境可双击根目录的 `医生学生权限测试.bat`，默认使用 `http://127.0.0.1:8013/` 和 `.local/issue_13_review/`。本机初始管理员 `aaa001`、医生 `ddd001`，密码均 `12345678`，仅用于隔离验收，不是公网密码。

## 自动验证与边界

`tests/test_team_permissions.py` 通过真实登录测试账号开通与隔离、越权、防确认绕过、授权期限/撤销、停用、原件与导入、OCR 运行中撤权。`tests/test_team_migration.py` 验证旧库升级、数据保留、Alembic 元数据一致和降级保护。Node 测试覆盖共用工作区、密码确认/清空和授权表单。

科研队列、批量导出仍为规划入口，本轮不提供导出授权或队列授权。#36 的同意撤回及完整管理页面、#37 的统一操作审计未在本轮实现；现有账号事件、审核事件和授权/撤销记录继续保留，因此不能将 #13 整体标记完成。

## 发布注意

需要先运行 Alembic 迁移，再切换代码。保存旧 release 和数据备份。已有学生账号时，不应直接用旧代码覆盖新版；旧代码不认识学生角色。若先发布功能分支供 IP 验收，应保留对应 Git 提交，验收合并 main 后再恢复正常 main 更新流程。现有服务器更新器会拒绝不包含运行提交的 main，避免误降级。
